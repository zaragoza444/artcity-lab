Separate product domain. Shared Art City AI core. Build the IP system before scaling generation.
1. Purpose and Implementation Directive
This document converts the Art City AI Vertical Drama IP Factory master specification into an execution-ready engineering backlog. It is designed for direct use by the technical lead, backend, frontend, AI/ML, DevOps and QA teams. The goal is to remove interpretation from the first build cycle: ticket boundaries, dependencies, coding sequence, acceptance gates and release criteria are defined here.
Do not build Vertical Drama as a generic prompt-to-video page.
Do not fork the Art City AI platform or duplicate accounts, billing, storage, project ownership or provider integrations.
Build a dedicated Vertical Drama domain with its own routes, services, tables and UI, linked to the canonical Art City AI project and asset systems.
Treat Story Bible, Canon, Character DNA, Episode State and Provenance as first-class data, not text blobs.
AI generation must remain provider-agnostic through the shared AI Router.
Sorani Kurdish (ckb-IQ), English and Arabic must be supported from the beginning; RTL is not a post-launch patch.
2. Architecture Freeze Before Coding
The following decisions are frozen for the first implementation unless Art City product leadership explicitly changes them. Developers should not silently replace them with convenient alternatives.
3. Delivery Team and Ticket Ownership
One engineer may hold multiple codes on a small team. The codes identify responsibility, not headcount.
4. Recommended Build Sequence and Release Train
4.1 Critical path
Shared project linkage → Vertical Drama domain schema → IP/Canon → Story Bible → Season/Episode versions → Scene/Shot model → AI jobs/assets → Assembly/QC → Delivery.
Do not start batch video generation before Character DNA, shot identity, versioning, provenance and cost attribution are functional.
Do not introduce analytics-driven rewriting until lock/version semantics are stable.
5. Sprint 0 — Foundation, Domain Boundary and Contracts
Sprint 0 exists to prevent the common failure mode where UI and model calls are built before the data model is stable. The output is a compilable, deployable skeleton with agreed contracts and no duplicated platform infrastructure.

7. Sprint 2 — Story Bible, Season Architecture and Episode Factory

9. Sprint 4 — Assembly, Localization, QC and Delivery Backlog

15. Frontend Build Order
16. Kurdish Sorani / RTL Release Criteria
Use Unicode UTF-8 end-to-end; never transliterate Sorani to store or process it internally.
ckb-IQ content direction is RTL, but IDs, timecodes, file names, URLs and technical fields may remain LTR inside isolated UI containers.
All multi-language content fields must store language code and content separately. Do not combine translations into one text column.
Test punctuation, Arabic-Indic/Latin digits, quotation marks, parentheses, colon/timecode display and mixed English model names inside RTL text.
Exported subtitles and metadata must preserve correct line order and encoding.
AI prompts may use internal English instructions, but the requested content language and cultural context must be explicit and the output schema language-tagged.
Golden tests must include Sorani character names, dialogue, long screenplay paragraphs and right-aligned form fields.
17. Automated Test Matrix
18. Definition of Done for Every Ticket
Code merged after peer review and linked to ticket ID.
API/schema change documented and contract tests updated.
RBAC and tenant/project isolation considered for every server endpoint.
Loading, empty, error, permission-denied and retry states implemented where relevant.
Logs include request/job correlation identifiers; no secrets or raw sensitive tokens logged.
User-facing text supports localization; no English-only hard-coded layout assumption.
Unit/integration tests cover happy path plus at least one important failure path.
No provider-specific AI call is added outside the shared AI Router/provider adapter layer.
AI-derived records include provenance and cost/usage metadata when applicable.
Database migration includes rollback or documented irreversible rationale.
QA evidence attached and acceptance gate explicitly marked pass/fail.
19. MVP Release Gate
Do not call the module production-ready simply because it can generate clips. The MVP is ready when one governed IP can travel through the complete core lifecycle with traceability and human approval.

22. Final Engineering Directive
The first success metric is not “we generated a vertical video.” It is “we created a governed entertainment IP whose story, canon, characters, episodes and generated production assets remain consistent, versioned, auditable and reusable.” Once that foundation works, Art City AI can change or add generation models without rebuilding the product.

Decision | Frozen rule
Product boundary | /vertical-drama is a dedicated product area under the existing Art City AI account and project shell.
Project identity | Every Vertical Drama title references the shared project_id; Vertical Drama also owns a vd_project_id/domain aggregate ID.
Asset identity | Generated/reference assets use the shared asset store and immutable asset IDs; Vertical Drama stores semantic links to those assets.
AI providers | No provider-specific calls from UI or domain services. All inference goes through the AI Router/model registry.
Canonical narrative data | Structured entities and versioned JSON are authoritative. Generated prose is a derivative representation.
Canon changes | Approved canon changes emit domain events and mark dependent material stale; they do not silently rewrite approved episodes.
Generation | All expensive generation is asynchronous, idempotent, retryable and cost-attributed.
IP/provenance | Human authorship, source/reference origin, model/provider, prompts, seeds/parameters and output IDs are logged.
Localization | Original-language content remains canonical; translated/adapted versions are linked variants.
Deletion | Soft delete + audit trail for project-domain entities; hard deletion only through privileged data-retention workflow.

Risk | Why it matters | Mandatory response
RISK-01 — Text blobs instead of domain data | Fast initially, disastrous for canon checks, localization, versioning and analytics. | Reject designs that store Story Bible/episode/character state as a single unstructured document.
RISK-02 — Provider lock-in | Direct fal.ai or other provider calls inside product code will make migration/cost routing difficult. | All inference through AI Router and workflow keys.
RISK-03 — Weak identity consistency | Video generation before reference-locking leads to changing faces, wardrobe and world continuity. | Block production when required Character DNA/reference bindings are missing.
RISK-04 — Silent AI rewrites | Regeneration can destroy approved creative work. | Immutable versions + approval locks + explicit new draft.
RISK-05 — Cost explosion | Batch video generation can create unexpected spend. | Estimate/guardrail/budget checks before enqueue; cost ledger after each attempt.
RISK-06 — RTL added late | Core forms/grids/editors become costly to repair. | Sorani golden project from Sprint 1 onward.
RISK-07 — Provenance gaps | Cannot prove origin, model use, or human contribution later. | Persist provenance at creation time, not as a future reporting feature.
RISK-08 — Cross-product coupling | Direct access to Cinema/Edit private tables creates brittle dependencies. | Use shared services or explicit contracts/events.
